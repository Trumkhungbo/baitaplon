💪 Điểm Mạnh & Điểm Yếu

✅ Điểm mạnh

  • PBKDF2 password hashing chuẩn (65 536 vòng, salt ngẫu nhiên)
  • Command Pattern đúng với CommandDispatcher + CommandHandler interface
  • ConcurrentHashMap cho auctions map → thread-safe lookup
  • Anti-sniping (gia hạn 60s khi bid trong 30s cuối) — tính năng cao cấp
  • AutoBid chain với safety counter tránh infinite loop
  • Prepared Statement toàn bộ DAO — không SQL injection
  • Migration tự động bảng auctions/bid_transactions
  • Dual-format protocol (JSON + pipe-delimited text)
  • Có unit test + concurrency test (AuctionServiceTest)
  • Dark-mode UI với color palette nhất quán (global.css)

❌ Điểm yếu lớn nhất

  • Client KHÔNG xác thực server-side — spoofing username dễ dàng
  • ResetPassword không yêu cầu xác thực danh tính trước
  • AuctionService tự new DAO trong constructor — vi phạm DI
  • Static global state (AuctionItems.list, StoreDataInput) toàn client
  • setServerListener() ghi đè listener cũ → mất message bất kỳ
  • AdminpageHandle.Confirm dùng UPDATE_STATUS thay vì APPROVE_AUCTION
  • ItemShowingHandle.RaiseBid dùng StoreItemDataInit.description làm auctionId
  • addAuction() luôn tạo item type Art — bỏ qua ELECTRONICS/VEHICLE
  • createAuction() tạo OPEN thay vì PENDING — bypass admin approval
  • Không có dequeue listener/timer → memory leak lớn khi switch scene

🏛️ Phần 1 — Kiến Trúc Tổng Thể

Critical AuctionService tự khởi tạo toàn bộ DAO → vi phạm DI và SRP AuctionService.java constructor

Vấn đề: Constructor gọi new BidHistoryDAO(), new AuctionStateDAO()... 5 lần. Cũng gọi DatabaseInitializer.initialize() — DB khởi tạo bên trong service layer.

Nguy hiểm: Không thể mock DAO để unit test; nếu DB không ready sẽ throw ở constructor; vi phạm SRP và DIP. AuthService.java cũng làm y chang.

Sửa: Inject qua constructor hoặc dùng factory. DB init phải ở application startup (ServerApplication.java).

// TRƯỚC (bad)
public AuctionService() {
    DatabaseInitializer.initialize();
    this.bidHistoryDAO = new BidHistoryDAO();
}

// SAU (good) — inject
public AuctionService(BidHistoryDAO bidHistoryDAO,
                      AuctionStateDAO auctionStateDAO, ...) {
    this.bidHistoryDAO = bidHistoryDAO;
    ...
}
High AuctionService là God Object — 500+ dòng, 10+ trách nhiệm AuctionService.java

Vấn đề: Một class vừa quản lý auction lifecycle, vừa xử lý bidding, vừa anti-sniping, vừa auto-bid chain, vừa persistence, vừa seeding data.

Sửa: Tách thành AuctionLifecycleService, BiddingService, AutoBidService. Persistence chỉ qua DAO layer.

Medium Command layer không có validation layer riêng AddAuctionCommand.java, BidCommand.java

Vấn đề: Validation logic (price > 0, parts.length checks) nằm trực tiếp trong CommandHandler. Mỗi command lặp lại cùng pattern.

Sửa: Tạo RequestValidator interface, inject vào command. Tách validation khỏi business logic.

Medium Không có DTO layer — string protocol bị parse ở nhiều nơi ClientHandler.java, AuctionItems.java, LobbypaneHandle.java

Vấn đề: Response format như AUCTION_LIST|id:name:type:info1:info2:price:status được parse bằng split(";") và split(":") ở nhiều controller client. Thay đổi format là break toàn bộ client.

Sửa: Dùng JSON format nhất quán (đã có Gson). Common module có DTO classes, server serialize, client deserialize.

⚙️ Phần 2 — Backend / Socket Server

Critical createAuction() tạo OPEN ngay — bypass hoàn toàn admin approval flow AuctionService.java:createAuction()

Vấn đề: Hàm createAuction() tạo auction với AuctionStatus.OPEN. Trong khi đó createPendingAuction() mới dùng PENDING. Hàm addAuction() delegate tới createAuction() → tất cả auction cũ không cần admin approve vẫn live ngay.

Nguy hiểm: Seller có thể bán sản phẩm không được kiểm duyệt. Logic nghiệp vụ sai hoàn toàn với flow PENDING→OPEN.

Sửa: createAuction() phải dùng AuctionStatus.PENDING. Chỉ approveAuction() mới chuyển sang OPEN.

Critical isActiveAuction() bao gồm PENDING — bidder có thể bid vào auction chưa duyệt AuctionService.java:isActiveAuction(), placeBid()

Vấn đề: isActiveAuction() trả về true cho PENDING. Trong placeBid(), chỉ check PENDING ở block sau — nhưng block đầu gọi finishAuction() nếu hết giờ, và bỏ sót case "auction PENDING chưa start".

// HIỆN TẠI — PENDING bị coi là active
private boolean isActiveAuction(Auction a) {
    return a.getStatus() == OPEN || a.getStatus() == RUNNING
           || a.getStatus() == PENDING; // ← BUG
}

// ĐỀ XUẤT
private boolean isActiveAuction(Auction a) {
    return a.getStatus() == OPEN || a.getStatus() == RUNNING;
}
High syncAuctionFromDatabase() gọi trong mọi read — N+1 query problem AuctionService.java:getAuctionList(), closeExpiredAuctions()

Vấn đề: getAuctionList() iterate qua mọi auction, mỗi cái gọi syncAuctionFromDatabase() → 1 DB query/auction. 100 auctions = 100 queries/lần gọi LIST_AUCTIONS.

Sửa: Cache in-memory đã có (ConcurrentHashMap), đừng sync từ DB mỗi lần. Chỉ sync khi cần thiết (sau restart, hoặc theo TTL).

High BroadcastService.broadcastBidUpdate() không thread-safe với sendMessage() BroadcastService.java, AuctionServer.java:broadcastToAuctionRoom()

Vấn đề: broadcastToAuctionRoom() iterate connectedClients (ConcurrentHashMap.newKeySet() — OK), nhưng mỗi client.sendMessage() đã synchronized. Tuy nhiên broadcastBidUpdate call từ handler thread — nếu nhiều bid đồng thời, nhiều broadcast thread cùng iterate và gọi sendMessage trên cùng client. PrintWriter synchronized nên OK, nhưng thứ tự message có thể lộn xộn.

Sửa: Dùng ExecutorService riêng cho broadcast, hoặc queue message.

High addAuction() luôn tạo item type Art — ELECTRONICS/VEHICLE bị bỏ qua AuctionService.java:addAuction()

Vấn đề: Hàm legacy addAuction(sellerUsername, itemName, startPrice) tạo new Art(...) hardcode. Nếu client gọi lệnh ADD_AUCTION 4-field, sẽ bypass type selection.

// BUG: luôn là Art bất kể type
Item item = new Art(itemName, "No description", startPrice, "",
                    "Unknown", Calendar.getInstance().get(YEAR));
High Auction monitor chạy mỗi 1 giây — gọi closeExpiredAuctions() liên tục AuctionServer.java:startAuctionMonitor()

Vấn đề: Mỗi tick gọi closeExpiredAuctions() → iterate toàn bộ auctions, mỗi cái lock + sync DB. Với nhiều auction, CPU spike đáng kể.

Sửa: Tăng interval lên 5-10s. Hoặc dùng ScheduledExecutorService với delay tính từ endTime thực tế.

Medium MAX_CLIENT_THREADS = 50 hardcode — không configurable AuctionServer.java

Vấn đề: Thread pool cố định 50, không có backpressure khi vượt. Nên dùng Executors.newCachedThreadPool() hoặc config từ properties file.

Medium closeExpiredAuctions() có logic ngược — ưu tiên local endTime thấp hơn DB AuctionService.java:closeExpiredAuctions()

Vấn đề: Sau khi sync DB, nếu localEndTime < auction.getEndTime() (DB đã extend do anti-sniping), code lại gán lại local time thấp hơn → auction bị đóng sớm hơn dự định.

// BUG: ghi đè endTime DB bằng local cũ hơn
long localEndTime = auction.getEndTime();
syncAuctionFromDatabase(auction);
if (localEndTime < auction.getEndTime()) {
    auction.setEndTime(localEndTime); // ← SAI: đây là giá trị cũ hơn
}

Sửa: Bỏ block đó đi. Sau sync, dùng endTime từ DB là chuẩn.

🔐 Phần 3 — Auth & Security

Critical Client tự gửi sellerUsername — có thể spoof, đăng bán giả danh người khác AddAuctionCommand.java, ClientHandler.java

Vấn đề: Command ADD_AUCTION nhận sellerUsername = parts[1] từ client. Có kiểm tra sellerUsername.equals(client.getCurrentUser()) — tốt. Tuy nhiên GET_ACCOUNTINFORMATION nhận username từ client không verify:

// GetAccountInformationCommand.java
String username = parts[1]; // ← bất kỳ client nào gửi username khác đều được

Sửa: Với GET_ACCOUNTINFORMATION, luôn dùng client.getCurrentUser() thay vì parts[1].

Critical ResetPassword không yêu cầu FORGOT_PASSWORD verification trước AuthService.java:resetPassword(), ResetPasswordCommand.java

Vấn đề: Client có thể gửi thẳng RESET_PASSWORD|username|newPassword mà không cần qua FORGOT_PASSWORD flow. Server xử lý thẳng không kiểm tra session state.

Nguy hiểm: Attacker biết username có thể reset mật khẩu của bất kỳ ai.

Sửa: Server cần lưu "reset token" sau FORGOT_PASSWORD thành công, RESET_PASSWORD phải gửi token đó. Hoặc ít nhất kiểm tra phone+personalID trong RESET_PASSWORD.

High PasswordHasher.matches() có plain-text fallback nguy hiểm PasswordHasher.java:matches()

Vấn đề:

if (!storedValue.startsWith(PREFIX)) {
    // Fallback: so sánh plain-text bằng byte comparison!
    return MessageDigest.isEqual(rawPassword.getBytes(), storedValue.getBytes());
}

Nếu ai đó insert user với password plain-text vào DB (SQL injection, admin access...), họ vẫn đăng nhập được.

Sửa: Fallback nên return false, log warning. Không bao giờ accept plain-text password.

High AdminpageHandle dùng UPDATE_STATUS thay vì APPROVE_AUCTION AdminpageHandle.java:Confirm()

Vấn đề:

// Admin client gửi
StartScence.client.sendMessage("UPDATE_STATUS|" + item.getIteminfomation() + "|OPEN");

UPDATE_STATUS command không check client.isAdmin(). Bất kỳ bidder nào cũng có thể gửi UPDATE_STATUS để approve auction của mình.

// UpdateStatusCommand.java — không có auth check!
public void handle(String[] parts, ClientHandler client) {
    if (!client.isLoggedIn()) { ... } // ← chỉ check logged in, không check isAdmin()
    String response = auctionService.updateStatus(parts[1], newStatus);
}

Sửa: Admin UI dùng APPROVE_AUCTION. Hoặc thêm if (!client.isAdmin()) vào UpdateStatusCommand.

Medium Không có rate limiting — có thể spam bid/register AuctionServer.java, ClientHandler.java

Vấn đề: Không có limit số request/giây từ một client. Attacker có thể flood server với hàng nghìn bid/giây, hoặc brute force password.

Sửa: Thêm per-client request counter với sliding window. Disconnect nếu vượt threshold.

Low DatabaseInitializer dùng SQL string formatting cho seed data DatabaseInitializer.java 
// Không phải injection vì hash là từ hàm nội bộ, nhưng style xấu
st.execute("INSERT OR IGNORE INTO users ... VALUES ('seller1', '" + sellerHash + "'...)");

Sửa: Dùng PreparedStatement cho tất cả INSERT, kể cả seed data.

🎨 Phần 6 — Frontend / JavaFX UI

Critical setServerListener() ghi đè listener cũ — mất tất cả global broadcasts SocketClient.java, ItemShowingHandle.java:RaiseBid(), LoginHandle.java:Login()

Vấn đề: SocketClient chỉ có 1 listener. Mỗi lần click "Bid" hay "Login", controller ghi đè listener toàn cục:

StartScence.client.setServerListener(message -> {
    Platform.runLater(() -> {
        if (message.startsWith("BID_SUCCESS|") || message.startsWith("BID_UPDATE|")) {
            status.setText("RUNNING");
        }
    });
});
// ← Mọi message khác (AUCTION_CLOSED, LOBBY_UPDATE...) bị nuốt mất!

Hậu quả: Auction đóng không notification; lobby không update realtime; mọi server message ngoài BID_SUCCESS đều mất.

Sửa: Dùng publish-subscribe. SocketClient expose addListener(topic, handler) / removeListener(). Message routing theo prefix.

// Ví dụ đơn giản:
public class MessageRouter {
    private final Map<String, Consumer<String>> handlers = new ConcurrentHashMap<>();
    public void register(String prefix, Consumer<String> handler) { ... }
    public void route(String message) {
        handlers.entrySet().stream()
            .filter(e -> message.startsWith(e.getKey()))
            .forEach(e -> e.getValue().accept(message));
    }
}

⚡ Phần 7 — Realtime & Multithreading

High Auction state update không atomic với DB persist AuctionService.java:placeBid()

Vấn đề: Trong placeBid(), sau khi update in-memory auction state (setCurrentPrice, setHighestBidder), code gọi bidHistoryDAO.save() rồi persistAuctionState(). Nếu DB fail sau khi update memory, rollback đúng — tốt. Nhưng giữa lúc bidHistoryDAO.save() thành công và persistAuctionState() bắt đầu, nếu server crash → bid history được lưu nhưng auction state không update → inconsistent.

Sửa: Wrap bidHistoryDAO.save() và persistAuctionState() trong cùng một DB transaction.

Medium Client listener thread không có reconnect logic SocketClient.java 
} catch (IOException e) {
    System.out.println("Disconnected from server."); // ← chỉ log, không reconnect
}

Vấn đề: Nếu server restart hoặc network drop, client bị disconnect vĩnh viễn. UI không thông báo. Không có retry.

Sửa: Exponential backoff reconnect. Notify user qua dialog khi mất kết nối.

Medium Broadcast sau bid không gửi endTime mới (sau anti-sniping) BroadcastService.java:broadcastBidUpdate()

✅ Checklist Test Manual Đầy Đủ

Auth Flow

  • Đăng ký tài khoản mới với đủ thông tin → nhận REGISTER_SUCCESS
  • Đăng ký username trùng → nhận REGISTER_FAILED
  • Đăng nhập đúng credentials → vào được Lobby
  • Đăng nhập sai password → hiển thị FailedLogin
  • Đăng nhập để trống username/password → hiển thị SomeThingUnFill
  • Đăng nhập với tài khoản admin → vào được AdminPage
  • Forgot password với thông tin đúng → nhận SUCCESS
  • Forgot password với thông tin sai → nhận FAILED
  • Reset password → đăng nhập lại với password mới thành công
  • Thử RESET_PASSWORD trực tiếp qua socket không qua FORGOT_PASSWORD → phải bị chặn

Seller Flow

  • Seller đăng sản phẩm ELECTRONICS với brand + warrantyMonths → lưu đúng DB
  • Seller đăng sản phẩm ART với artist + creationYear → lưu đúng DB
  • Seller đăng sản phẩm VEHICLE với engineType + mileage → lưu đúng DB
  • Sản phẩm sau khi đăng có status PENDING (chưa duyệt)
  • Seller thấy sản phẩm của mình trong InvesmentWait
  • Seller KHÔNG thể bid vào auction của chính mình

Admin Flow

  • Admin thấy danh sách PENDING items trong AdminPage
  • Admin tick chọn item và Confirm → item chuyển OPEN
  • Item OPEN xuất hiện trong Lobby của bidder
  • Admin không thể bid (không có UI bidding cho admin)
  • Thử UPDATE_STATUS|{id}|OPEN từ bidder account → phải bị từ chối

Bidding Flow

  • Bidder thấy danh sách auction OPEN/RUNNING trong Lobby
  • Click vào auction → vào ItemShowing với thông tin đúng
  • Bid cao hơn giá hiện tại → nhận BID_SUCCESS, giá update realtime
  • Bid thấp hơn hoặc bằng giá hiện tại → nhận ERROR
  • Bid sau khi auction đóng → nhận ERROR|Auction is not available
  • Hai client bid cùng lúc → chỉ một thắng, client còn lại thấy giá mới
  • Bid trong 30s cuối → endTime tự động extend 60s (anti-sniping)
  • Đặt AutoBid với maxBid và increment → tự động outbid khi người khác bid

Auction Lifecycle

  • Auction hết giờ → tự động đóng, thông báo AUCTION_CLOSED broadcast
  • Auction đóng có winner → getWinner trả về đúng winner + finalPrice
  • Auction đóng không có bid → winner = NONE
  • closeAuction thủ công (admin) → hoạt động đúng
  • Restart server → load lại đúng auctions từ DB
  • Restart server → bid history không mất
  • Restart server → auction đang RUNNING vẫn tiếp tục đúng endTime

Realtime

  • Client A bid → Client B đang xem cùng auction thấy BID_UPDATE ngay lập tức
  • Client A bid → Lobby của Client C thấy giá mới trong AUCTION_LIST update
  • Disconnect một client → server tiếp tục bình thường, không crash
  • 10+ client kết nối cùng lúc → server xử lý ổn định
  • Bid storm (nhiều bid liên tiếp) → không deadlock, không data corruption

"Nếu 100 người bid cùng lúc, hệ thống xử lý thế nào?" Thread safety, synchronized block Mỗi auction có synchronized block riêng. ConcurrentHashMap cho concurrent access. Chỉ 1 thread/auction xử lý bid tại một thời điểm.
"Làm sao đảm bảo buyer không bid thấp hơn giá hiện tại?" Race condition check Check amount <= currentPrice trong synchronized block → atomic. Nếu 2 bid đến cùng lúc, cái thứ 2 thấy giá đã update của cái thứ 1.
"Hệ thống có thể bị SQL injection không?" PreparedStatement usage Toàn bộ DAO dùng PreparedStatement với parameter binding. Không có string concatenation trong SQL. Tuy nhiên DatabaseInitializer seed data dùng format string — điểm yếu.
"Password lưu như thế nào?" Password security PBKDF2WithHmacSHA256, 65536 iterations, 16-byte salt random. Timing-safe comparison qua MessageDigest.isEqual(). Có upgrade path từ plain-text.
"Nếu server crash giữa chừng bid, dữ liệu có bị mất không?" Transaction atomicity Có rollback in-memory nếu DB fail. Nhưng bidHistoryDAO.save() và persistAuctionState() không trong cùng transaction → có thể inconsistent (đây là điểm yếu thực tế).
"Anti-sniping hoạt động thế nào?" Business logic Nếu bid trong 30s cuối (ANTI_SNIPE_THRESHOLD_MS = 30000), tự động extend thêm 60s (ANTI_SNIPE_EXTENSION_MS = 60000). Áp dụng cả cho auto-bid chain.
"Admin approve auction như thế nào? Có bị bypass không?" Authorization APPROVE_AUCTION command check isAdmin(). Tuy nhiên UPDATE_STATUS command KHÔNG check admin → đây là lỗ hổng thực tế trong code.
"Có design pattern gì trong dự án?" Design patterns knowledge Command Pattern (CommandDispatcher + CommandHandler), Observer/Listener (ServerListener interface), Singleton (DatabaseManager), DAO Pattern, Facade (AuctionService).
"Tại sao cần auction_runtime_state ngoài auctions table?" Database design auction_runtime_state lưu in-memory state (current price, highest bidder, bid count) cho fast access. auctions là record lịch sử. Tuy nhiên hiện tại có redundancy — điểm yếu có thể nhận xét thẳng.
"Protocol giao tiếp client-server là gì, có handle lỗi parse không?" Protocol robustness Dual protocol: JSON (primary) và pipe-delimited text (fallback). Parse lỗi có try-catch. Tuy nhiên malformed JSON vẫn fallback sang pipe split — nếu cả hai fail thì command = empty string gây ERROR response.
